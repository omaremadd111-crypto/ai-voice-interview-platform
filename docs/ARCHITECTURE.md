# Architecture and engineering safeguards

## Purpose

The AI Voice Interview Platform separates recruiter and candidate presentation layers from the interview, evaluation, and scoring core. The design supports deterministic local demonstrations and provider-backed voice interviews without creating parallel implementations of interview behavior.

## System boundaries

```text
React / Gradio / FastAPI / LiveKit
                 |
        application services
                 |
      InterviewAgentService
        /        |        \
interview     LLMService   scoring/reporting
engine            |              |
             provider adapters   rubrics.json
                 |
          repository interfaces
                 |
             PostgreSQL
```

- Presentation layers are presentation only. UI callbacks, React components, and API routers do not implement interview flow, follow-up limits, scoring, or evaluation.
- Every transport calls application services and `InterviewAgentService`; LiveKit is used only as a transport/conversation channel and must never become a second interview implementation.
- Public applications reuse the existing candidate, CV parsing, and interview-plan services and must never become a second application pipeline.
- Provider SDKs are confined to their integration packages. Agents depend on `LLMService`, email callers depend on `EmailPort`, persistence callers depend on repository interfaces, and voice callers depend on LiveKit ports.
- Mock Mode is the default and completes the core flow without credentials. Simulated content is explicitly labeled.

## Major runtime components

| Component | Responsibility |
| --- | --- |
| React frontend | Recruiter dashboard, public job application, signed interview landing, and browser voice experience |
| FastAPI | Authentication, validation, authorization, serialization, and transport composition |
| Application services | Position, candidate, plan, pipeline, invitation, queue, interview, email, and screening use cases |
| InterviewAgentService | Single high-level interview orchestration API shared by all transports |
| InterviewEngine | Deterministic question state, answer submission, and follow-up budgets |
| Background worker | Queue claiming, leases, retries, prewarming, post-interview evaluation, invitation expiry, and email dispatch |
| PostgreSQL repositories | Durable HR, candidate, interview, queue, transcript, recording, and outbox state |
| LiveKit integration | Browser audio transport, STT/TTS/voice inference, participant tokens, room lifecycle, and optional egress |
| LLM adapters | Structured model operations behind `LLMService`; deterministic Mock Mode is always available |

## Interview and evaluation authority

The interview engine is the authority for question order, state transitions, and follow-up limits. Voice-specific services may classify conversational intent, coordinate silence, and adapt delivery, but they cannot bypass the engine.

Retrieval and memory are input-side only. If Mem0 or Qdrant is introduced later, it may inform what the agent asks or how a question is phrased, but it must never reach the evaluator, overall score, or screening outcome. Neither integration is currently implemented.

Scoring is deterministic:

- a category requires at least one transcript-traceable evidence item;
- without evidence, `score=None`, `sufficient_evidence=False`, and the reasoning is `Insufficient evidence`;
- the overall score and recommendation label are computed in Python from `config/rubrics.json`, never generated by an LLM;
- `PASS`, `FAIL`, and `NEEDS_REVIEW` are configurable initial screening results based on score, evidence coverage, and the position threshold;
- `PASS` does not mean "hire", `FAIL` does not mean "rejected", and the human recruiter remains the final decision maker.

## Position approval and public applications

For the automated pipeline, plan approval happens at the position level. A recruiter approves a position-level screening template before publication. Each applicant's interview plan is materialized from that approved template, without a separate per-candidate approval step. Editing the template or relevant position configuration revokes approval and unpublishes the position.

The manual per-candidate generate, edit, and approve flow remains available outside the automated pipeline. Public application routes are registered only when `PUBLIC_APPLICATIONS_ENABLED=true`.

## Queue, invitation, and email reliability

Workers claim queue rows atomically, use renewable leases, and retry recoverable failures with deterministic backoff. More than one worker can safely process a queue without screening the same candidate concurrently.

Invitation email is best-effort and additive. A failed, delayed, or unconfigured email send must never block a candidate from starting: the confirmation link and bookmarked `/interview/{token}` route remain usable. The email outbox uses a per-invitation idempotency key, deterministic retries, and a recruiter-visible terminal failure. Automated reminder emails are not implemented.

## Security and privacy invariants

- Credentials come from ignored environment files and are never hardcoded.
- Logs must not include keys, document text, candidate answers, email addresses, email bodies, or invitation tokens; operational logging uses lengths and hashes where needed.
- Session stores return deep copies and preserve candidate isolation.
- LiveKit credentials remain server-side, and participant tokens are short-lived.
- Recordings are disabled by default and require configured S3-compatible storage when enabled.
- Candidate-visible routes do not expose recruiter-only questions, rubrics, scores, or internal identifiers.

The platform must never implement emotion analysis, accent analysis, personality inference, biometric inference, facial analysis, protected-attribute inference, hiring decisions based on voice characteristics, or autonomous final hire/reject decisions. Voice is used only to carry conversation.

## Current exclusions

The repository does not include outbound PSTN/telephone calling, ATS integration, calendar integration, automated reminder emails, payments, OCR for scanned documents, Mem0/Qdrant memory, or deployment infrastructure. These are not implied by the interfaces or current architecture.
